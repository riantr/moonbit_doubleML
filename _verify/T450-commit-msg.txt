Release 0.44.0: PSProcessorConfig cv_calibration abort -> raise PSConfigError

Continuing the surgical abort -> raise conversion pattern from
v0.35.0-v0.43.0. This release tackles the inconsistent-
configuration defensive guard in PSProcessorConfig::new
(ps_processor.mbt:35).

  - kfold.mbt: declare pub suberror PSConfigError with
    InconsistentCVCalibration variant (no payload).
  - ps_processor.mbt::PSProcessorConfig::new: signature
    `PSProcessorConfig` -> `PSProcessorConfig raise
    PSConfigError`. The `abort("cv_calibration=true requires
    calibration_method='isotonic'")` is replaced with
    `raise PSConfigError::InconsistentCVCalibration`.
  - ps_processor.mbt::PSProcessorConfig::default: refactored
    to construct the default `PSProcessorConfig` literal
    directly instead of going through the (now-`raise`) `new()`
    path. The default args are valid, so the cv_calibration
    abort is unreachable in practice.

New regression test (ps_processor_test.mbt):
  - ps_processor_config_raises_inconsistent_cv_calibration:
    calls `PSProcessorConfig::new(calibration_method="none",
    cv_calibration=true)` and asserts the error fires. Uses
    `try ... catch ... noraise { fail(...) }` pattern.
    Mutation-verified: removing the validation block makes
    the test fail with the expected diagnostic.

Public API stability:
  PSProcessorConfig::new is the only signature change. All
  cascade callers (PSProcessor::new, PSProcessor::from_config,
  DoubleMLDID*::new family) continue to work unchanged
  because the new raise is only triggered by an
  inconsistent configuration that no prod code produces.
