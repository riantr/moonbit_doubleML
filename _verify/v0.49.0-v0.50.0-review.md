# Post-release review — v0.49.0 + v0.50.0

## Summary

Both releases pass the full MoonBit gate: 4 backends report 325/325 tests with
`--deny-warn`, all 23 in-tree validators (including the new
`validate_apos_with_python.py` and `validate_cvar_with_python.py`) end with
`PASS` or `Reference:`, and the new `cmd/apos` and `cmd/cvar` demos both print
`PASS` and exit 0 on the canonical DGP. The new code is in idiomatic shape for
the package: every public accessor uses the v0.48.0 cascade wrap, no
spurious `raise` in signatures, no naked `print` in non-`cmd/` paths, and
all new `pub fn` / `pub struct` carry `///|` docstrings.

What I found is a small pile of **docstring-vs-code drift** in the new
`DoubleMLAPOS::causal_contrast` and the `DoubleMLAPOS::fit` inline comment,
plus a `moon fmt` diff that the release tag should have caught, plus a
handful of `for x in arr` foreach loops in cvar.mbt that will surface as
`moon prove` blockers the next time someone tries to put a contract on
`cvar_inner_crossfit`. None of these are runtime bugs — the estimators are
correct, the validators are tight, and the releases are shippable as-is.
But the documentation claims are misleading enough that I would file
follow-ups before v0.51.0 opens.

Verdict: **RELEASE_READY** (with one nit: `moon fmt` diff is a process
gap, not a release blocker).

## Findings

### Critical (must-fix before v0.51.0)

None. The estimators are correct, the tests are tight, the validators
PASS. The two docstring bugs below are not runtime bugs.

### Major (should-fix)

1. **`DoubleMLAPOS::causal_contrast` docstring misstates the return
   shape (apo.mbt:388–394).** The docstring says:

   > Returns one `Array[Double]` of length `treatment_levels.length()`
   > per reference level: the i-th entry is `coefs[i] - coefs[ref_idx]`

   The actual implementation (apo.mbt:441–452) interleaves `(delta, se)`
   pairs for every non-reference index and pushes a single `0.0` for the
   reference index, so each row is `1 + 2 * (n - 1) = 2n - 1` entries
   long, not `n`. The test (`apo_test.mbt:73–83`) and the cmd demo
   (`cmd/apos/main.mbt:76–77`) both use the actual shape:
   `contrasts[0][1]` is the delta and `contrasts[0][2]` is the SE. The
   test comment block on `apo_test.mbt:73–76` has the right shape
   description; the public function docstring does not. Any downstream
   user reading the docstring will be confused. Fix: rewrite the
   `///` block on `causal_contrast` to match the `(0.0, delta_0, se_0,
   delta_1, se_1, ...)` layout, and note that the SE is the conservative
   `sqrt(se_i^2 + se_ref^2)` quadrature (the second paragraph already
   says this — the first is the one that's wrong).

2. **`DoubleMLAPOS::fit` inline comment names a non-existent helper and
   contradicts the actual code (apo.mbt:317–322).** The comment claims
   the parent "fits each child APO with `n_rep = 1`" and uses "the
   parent's stratified fold partition via the internal
   `fit_with_splits` helper". Neither is true: the code passes
   `n_rep=self.n_rep` (line 327), there is no `fit_with_splits` helper
   anywhere in the tree (grep'd across `*.mbt`), and the child
   `DoubleMLAPO::fit` calls the regular `kfold(n, self.n_folds, ...)`
   (apo.mbt:181), not `kfold_stratified`. The CHANGELOG entry for
   v0.49.0 says the right thing (`n_rep` is now passed through, fold
   count is `n_rep * n_folds * n_treatment_levels`) — the inline
   comment is the only thing wrong. Fix: rewrite the `//` block to
   "v0.49.0: the parent APOS passes `n_rep` straight through to each
   child `DoubleMLAPO`, which runs the regular (non-stratified) k-fold
   partition; total fold draws per treatment level = `n_rep`."

3. **`DoubleMLAPOS` struct docstring claims stratified folds that the
   children don't actually use (apo.mbt:227–229).** The struct doc
   says "Each treatment level is fit with the same fold partition
   (stratified by `data.d` to balance every level across folds)". The
   child `DoubleMLAPO::fit` uses `kfold(n, self.n_folds, ...)`, not
   `kfold_stratified`, so the "stratified by `data.d`" claim is false.
   Note this is a docstring bug, not a numerical bug — the validators
   pass. If the next release actually wants to use `kfold_stratified`
   for the per-level fits, that's a follow-up worth filing; otherwise
   just remove the "stratified by `data.d`" sentence.

### Minor (worth-fix)

4. **`moon fmt` diff on the new code (3 files, 5 hunks).** Running
   `moon fmt --check` against HEAD produces non-empty diffs for:
   - `apo.mbt:447–448` — leading whitespace on the continuation line
     of the `(se * se + se * se).sqrt()` expression.
   - `kfold.mbt:239` — missing blank line before the `///|` for
     `kfold_stratified` (the formatter wants a blank between the
     previous doc block and the new function header).
   - `kfold.mbt:339–348` — nested `if/else` with `f == 0` can be
     flattened to `else if f == 0 { ... } else { ... }`; the formatter
     prefers the flattened form.
   - `cmd/apos/main.mbt:54` — `0.5 * xsum + eps` should be wrapped.
   - `cmd/apos/main.mbt:71–72, 78–79` — three `println` calls exceed
     the 80-column line budget; the formatter wraps them.

   This is a release-process gap (the `v0.50.0` and `v0.49.0` tags
   should have been formatted). The diff is purely cosmetic — no
   runtime or semantic effect — and `moon fmt` is idempotent. Fix:
   `moon fmt` and amend the release commits (or open a v0.50.1 patch
   release with the fmt diff).

5. **`kfold_stratified` allocates a `key_of` array of size `n` and
   never reads it (kfold.mbt:280–318).** The `key_of : Array[String]`
   array is populated in the group loop (line 283) and then explicitly
   discarded with `let _ = key_of` (line 318) to silence the unused
   warning. The comment says "kept for debugging / parity with
   upstream doc" but the array is never read by any function. This is
   wasted O(n) memory and O(n) writes per `kfold_stratified` call. Fix:
   delete the `key_of` declaration, the inner `key_of[i] = key` write,
   and the `let _ = key_of` line.

6. **`cvar.mbt` adds 3 new `for x in arr` foreach loops in private
   helpers (lines 207, 446, 532).** Per `_verify/UPSTREAM_BLOCKERS.md`,
   `moon prove` cannot handle `for x in arr` in contracted scopes.
   These are not a runtime blocker (the validators pass), but they
   will surface as `moon prove` issues the first time someone tries
   to add a contract to `stratified_half_split` or
   `cvar_inner_crossfit`. For a v0.51.0 contract pass, convert them
   to `for i = 0; i < arr.length(); i = i + 1 { ... arr[i] ... }` to
   match the convention used in `kfold_stratified` and the rest of
   the public API.

7. **`cvar.mbt::predictions_m` treatment=0 flip is documented but
   untested at the m_hat level (cvar_test.mbt:141–158).** The
   `cvar_accessors_match` test verifies that `predictions_m` is
   clipped to `[clip, 1 - clip]`, and the
   `cvar_treatment_zero_swaps_outcome` test verifies the coef
   changes for `treatment=0`. But there is no test that pins
   `predictions_m()[i] == 1.0 - predictions_m_for_treatment_1[i]`
   (or similar) when `treatment=0`. The flip is implemented (line
   638–646) and documented (line 173–175) but the test only verifies
   the coef-level consequence. Add a test in v0.51.0.

8. **CHANGELOG v0.50.0 claims "6 public accessors" but lists 8 names
   and the file actually has 8 (cvar.mbt:105–183).** The list of
   `coef`, `se`, `confint`, `predictions_g`, `predictions_m`,
   `n_obs`, `n_features`, `fitted` is 8; the prose says 6. Fix the
   count to 8 in the CHANGELOG. The accessor set is correct.

9. **`cmd/cvar/main.mbt` uses the long form `@mavis/moonbit_doubleML.Matrix::zeros`
   while every other `cmd/*/main.mbt` (including the freshly-added
   `cmd/apos/main.mbt`) uses the short `@dml.Matrix::zeros` (cmd/cvar/
   main.mbt:21, 28, 31).** Both forms are equivalent — `mavis/moonbit_doubleML` is
   the import name and `dml` is the last segment — but the
   inconsistency reads like a copy-paste oversight. Fix: replace
   `@mavis/moonbit_doubleML.` with `@dml.` in `cmd/cvar/main.mbt` for consistency
   with the rest of the `cmd/` tree.

### Nit (style)

10. **Test canonical DGP uses `i % 2 == 0` for `d`** (apo_test.mbt:8,
    39, 62; cvar_test.mbt via `quantile_test_data()` in
    quantile_test.mbt:5). The prompt flagged this as a smell because
    it puts `d=0` in fold 0 and `d=1` in fold 1, which is a
    degenerate DGP for IPW. The new tests compensate with wide
    tolerances (`2 * se + 0.05`, hand-rolled-vs-true within 0.1),
    but a stratified DGP would tighten the bands and exercise the
    fold partition more honestly. Out of scope for this review
    (pre-existing test data generator), but worth a v0.51.0
    follow-up to add a `stratified_test_data()` helper that mixes
    `d` randomly rather than alternately.

11. **`solve_ipw_root` does not handle the empty-slice case
    (cvar.mbt:312–313).** The function unconditionally reads
    `y_slice[0]`, which will throw on an empty slice. The current
    call site (`cvar_inner_crossfit:518–520`) is safe because
    `stratified_half_split` always returns a non-empty `train_1`,
    but the function is private and could be called from a future
    edge-case path. Add a `require(y_slice.length() > 0)` (or
    early-return `0.0`) for symmetry with `cvar_ipw_score` (which
    has the empty guard at line 276).

12. **`cvar.mbt::DoubleMLCVAR::new` docstring lists `treatment` as
    "binary potential outcome to target (0 or 1; default 1)" but
    the `require(treatment == 0.0 || treatment == 1.0)` check (line
    74) is binary.** The docstring is consistent with the
    `require` (both say binary), so this is a "no finding", but
    worth a one-line clarification that the upstream Python
    restricts `treatment` to `{0, 1}` via a similar check.

## Verdict

**RELEASE_READY** — the v0.49.0 and v0.50.0 tags are functionally
correct and shippable as-is. The validators, the 4 backends, and the
cmd demos all pass. The 12 moon-check warnings are pre-existing and
unrelated. The 3 docstring/comment mismatches in `DoubleMLAPOS` are
misleading but not runtime bugs; the `moon fmt` diff is a process gap;
the `for x in arr` foreach loops in cvar.mbt are future-proofing
items. None of these justify a hot-fix release; they should be
addressed before v0.51.0 opens its contract pass.

## Recommended actions (in priority order)

1. **Major #1 — #3**: rewrite the 3 misleading docstrings/comments
   in `apo.mbt` (the public `causal_contrast` docstring, the
   `DoubleMLAPOS::fit` inline comment, and the `DoubleMLAPOS`
   struct docstring). One file, ~10 lines, low risk. Ship in
   v0.50.1 or the first v0.51.0 prep PR.
2. **Minor #4 — `moon fmt`**: run `moon fmt` and amend the v0.50.0
   release commit. This unblocks anyone running `--check` in CI
   later.
3. **Minor #5 — `key_of` dead array**: delete the unused
   `key_of : Array[String]` allocation in `kfold_stratified`.
   One file, ~3 lines.
4. **Minor #6 — foreach loops in cvar.mbt**: convert the 3 new
   `for x in arr` loops in `cvar.mbt` to index-based form before
   any v0.51.0 `moon prove` work. Pairs with the existing
   `UPSTREAM_BLOCKERS.md` "foreach-in-contracted-scope" issue.
5. **Minor #7 — `predictions_m` flip test**: add a
   `cvar_predictions_m_flips_for_treatment_zero` test that pins
   the docstring'd `1 - m` swap. Pin the symmetry at the m_hat
   level, not just the coef level.
6. **Minor #8 — CHANGELOG count**: fix "6 public accessors" to
   "8 public accessors" in the v0.50.0 CHANGELOG entry.
7. **Minor #9 — `cmd/cvar/main.mbt` import alias**: replace
   `@mavis/moonbit_doubleML.` with `@dml.` for consistency with the other
   `cmd/*/main.mbt` files.
8. **Nit #10 — #12**: out of scope for this review; file as
   v0.51.0 follow-ups.
