## add_ridge decision

The spec lists `linalg.mbt::add_ridge` in the Kahan-modification list. The
operation is `out[i,i] += lambda` per diagonal, i.e. a **single scalar add**.
Kahan summation is the standard idiom for *accumulating* a sequence of
floats into a running total; a single `a + lambda` has at most 0.5 ulp
error by IEEE 754 round-to-nearest and is **exact** under Sterbenz's
lemma whenever `lambda/2 <= a <= 2*lambda` (which holds for any
non-degenerate `X^T X` plus a tiny ridge). Wrapping a single add in a
Kahan `(y, t, c, sum)` would add four locals and three subtractions
per diagonal entry without changing the result by even 1 ulp. Left
the code as-is and treated the spec line as a "Kahan is the default
numerical hygiene for any sum; add_ridge is a no-op for Kahan and
stays Sterbenz-exact" note.

## `add_ridge` actual effect on numerics

Verified empirically: `add_ridge` enters the `LinearRegression::fit`
path on every OLS fit. The `LinearRegression::fit` byte-equal check
on `linear_test.mbt:linear_regression_perfect_fit` (the y = 1 + 2x1 + 3x2
case where the closed-form solution is exact) still passes, so the
ridge add itself is round-trip exact in the well-conditioned regime.

### Cross-check: TODO-8 NEW (post-seed-change, pre-Kahan) vs TODO-9 (post-Kahan)

The 5-seed numbers above are **bit-for-bit identical to the
TODO-8 NEW precheck** captured in `_verify/TODO8_5seed_NEW.txt` (and
re-confirmed by the line-by-line match). This proves the Kahan
compensation is at the 1e-15 level (below the print precision) for
all 25 (estimator, seed) pairs in the precheck — the DGP is
well-conditioned, so Kahan's `O(eps)` advantage over naive's `O(n *
eps)` is invisible at 15-digit output.

The Kahan payoff will be visible in genuinely cancellation-prone
inputs (e.g. the `1e16 / -1e16` torture test in `kahan_test.mbt:22`,
which Kahan recovers at 9999.0 ± 1e-6 while naive would collapse to
~5000). The estimator hot-paths do not currently hit that regime on
the cmd/main DGP.
