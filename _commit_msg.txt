publish.yml: fix moon.mod path (root → moonbit_doubleML/) for v0.53.0 release

The v0.53.0 tag push to github triggered .github/workflows/publish.yml,
which immediately failed at the "Resolve release version" step with
"Process completed with exit code 2". The reason: commit `fe2dd9c`
("project cleanup #4: root package → moonbit_doubleML/ subdir")
moved `moon.mod` from the repo root to `moonbit_doubleML/moon.mod`,
but publish.yml's version-extraction awk still read from the old
root path:

  manifest_version="$(awk -F'"' '/^version = / { print $2; exit }' moon.mod)"
                                                                ^^^^^^^^

The root no longer has a `moon.mod`, so `awk` produces empty
output, the version comparison fails, and the step exits non-zero
before the release ever gets a chance to compile or publish.

This is a pre-existing bug from the v0.52 cycle — v0.52.0 was
released without going through the github CI workflow (no v0.52.0
tag exists on github), so the broken path was never caught.

Fix: change the awk source path from `moon.mod` to
`moonbit_doubleML/moon.mod`. Single line, surgical.

After this commit, deleting the broken `v0.53.0` tag (locally +
on both remotes) and re-pushing it triggers a fresh
publish.yml run that gets past the version-resolution step.

No other path in publish.yml needs adjustment:
  - `moon check --target {native,wasm,wasm-gc,js} --deny-warn`
    runs from the repo root and picks up `moon.work` (16 members
    including `moonbit_doubleML/`)
  - `moon test --target ... --deny-warn` ditto
  - `moon info --target js` ditto
  - `moon fmt --check` ditto
  - `moon publish` runs from the root and detects the workspace
    member being published via moon.work
  - `typos` reads the repo
  - `gh release create` reads $GITHUB_REF_NAME which is `v0.53.0`
